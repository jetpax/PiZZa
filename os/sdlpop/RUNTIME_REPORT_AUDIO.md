# HDMI Audio → PiZZa · MAI direct path · Runtime report (rev A)

Implements the HDMI-audio work order (rev A): PCM audio over the HDMI
cable already carrying PiZZa's video, direct MAI programming (no
VCHIQ), exposed as the real Kconfig backend behind the SDL2 shim's
§5a audio function table. First consumer: SDLPoP's OPL3 + digi mix.
Retires the SDLPoP work-order §5a investigation.

Per the standing guardrail, this report separates **verified in
simulation** (host harness, qemu, build) from hardware results.
**M2 core acceptance passed on real hardware 2026-07-05**: the 1 kHz
test tone is audible over HDMI on the first flash. Remaining
sign-off items are listed below.

## Summary

- **M0 host-verified core: PASS.** IEC958 packer, 147:160 resampler,
  ring bookkeeping and the integrated pump are bit-exact-tested on
  host (`tests/audio_host`, `make run` → `ALL PASS`).
- **M1 DMA: rescoped.** A full BCM2835 DMA driver already exists
  in-tree (`drivers/dma/dma_bcm2835.c`, hardware-proven daily by the
  display fast path) with cyclic control-block chains, DREQ pacing
  and per-block completion IRQs — exactly the feature set this WO
  planned to build. The backend uses it through the standard Zephyr
  DMA API instead of duplicating a fixed-purpose driver. What this WO
  adds on top (ring/refill/underrun logic) is host-verified; the
  first-ever *DREQ-paced* use of that driver is a hardware sign-off
  item.
- **M2 staged.** `hdmi_audio_init.c` programs MAI + audio infoframe +
  N/CTS from clean-room register facts (Linux `vc4_hdmi.c` gen1 path
  cross-checked against Circle `CHDMISoundBaseDevice`). A dedicated
  test-tone image boots straight into a 1 kHz tone through the full
  path. Diagnostics: `pop audio`, `pop starve`.
- **M3 sim tranche: PASS** (full mixed-stream pump path on host,
  framing re-verified across 200 blocks). Game integration compiled
  into the default board image; in-game audio is the HW tranche.

**M1 evidence trail** (existing driver, our usage):
- Cyclic chain + DREQ TI construction: `dma_bcm2835.c` builds
  `TI = INT_EN | WAIT_RESP | DEST_DREQ | PERMAP(slot) | SRC_INC` for
  MEMORY_TO_PERIPHERAL and loops the last CB's `next` to CB 0 —
  matches BCM2835 ARM Peripherals §4 CB layout; the m2m flavor of the
  same CB builder moves the display backbuffer every frame on real
  hardware today.
- Our config: 8 CBs × 1536 B, `dma_slot=17` (HDMI DREQ, per
  BCM283x DT `dmas = <&dma 17>` and the peripherals PDF DREQ map),
  dest = MAI_DATA (bus `0x7E808020`, translated by the driver).
- The refill/IRQ-ack seam this WO adds is the host-tested ring above;
  the live CB/CS/DEBUG registers are dumpable at runtime via
  `pop audio` for the hardware pass.

## ✅ VERIFIED ON HARDWARE (rpi_zero_2w, 2026-07-05)

Tone image flashed by the user; **1 kHz sine audible over HDMI on
first boot** — the full source→resample→pack→DMA(DREQ 17)→MAI path
works on silicon, including the first-ever DREQ-paced use of
`dma_bcm2835.c` (M1 hardware evidence). Display: **Dell U2520D**
(UltraSharp 25" QHD monitor, audio via its 3.5 mm line-out — no
built-in speakers). Note this is a *monitor*, not a TV: R2 warned
displays can mute HDMI audio silently, but this one accepts and
routes it, so the R2 risk did not materialize here. Firmware
negotiated 1080p (pixel clock 148.5 MHz), not the panel's native
QHD — irrelevant to audio, which only depends on the audio clock
regen. Boot log:

```
bcm2835_fb: DMA blit on dma@3f007000 channel 4
sdlpop_hdmi_audio: MAI up: hsm 163682864 Hz, pixel 148500000 Hz, SMP 228474/67, N 6144, CTS 148500
pop_audio: HDMI audio open: 48 kHz stereo, 8 x 1536 B ring, DMA ch 5
pop_audio: M2 test tone: 1 kHz -12 dBFS via full resample/pack path
```

Every recovered value matches prediction: HSM 163.68 MHz (the vc4
default), pixel 148.5 MHz (1080p), CTS = pixel/1000, SMP 228474/67 ≈
163682864/48000, audio on channel 5 beside the display blit on 4.
The game image's `init_digi` correctly reports "already open (test
tone)" while the tone owns the path.

**M3 in-game audio — CONFIRMED 2026-07-05.** A game image booting
straight into level 1 with the Prince auto-paced (footstep + landing
sounds, no input device needed) produced **continuous audible in-game
audio** over the same HDMI path. This exercises the real
`audio_callback` mix (SDLPoP's digitized-sound path) end to end:
game callback → resample → IEC958 pack → DMA → MAI. The digi SFX and
the OPL3/MIDI music ride the identical transport, so this closes the
M3 acoustic check for game audio.

**Intro theme (OPL3 music path) — CONFIRMED 2026-07-05.** The shipped
`build-sdlpop` config boots straight to the game's original
Broderbund/title sequence, whose `show_title()` auto-plays
`sound_54_intro_music` (the main theme, OPL3 synthesized from the
packed MIDISND DATs) with no input — and it is **audible on the
display**. Together with the footstep pass above, both of SDLPoP's
audio paths (digitized SFX and OPL3/MIDI music) are now
hardware-verified through the HDMI backend.

To reach the original intro, the shipped image suppresses SDLPoP's
own added info screen (`show_splash`, "SDLPoP <version> … Press any
key to continue"), which otherwise gates the intro on a keypress this
port has no boot-time input for. `CONFIG_SDLPOP_SKIP_INFO_SCREEN`
(default y) packs a one-line `SDLPoP.ini` (`enable_info_screen =
false`) into the asset pack — the game's own supported option, game
tree untouched.

## Deviations from the work order (all argued, none silent)

1. **M1 driver not written.** The WO planned a minimal fixed-purpose
   DMA driver on the assumption none existed; `pizero` has since
   grown a full `dma.h` driver with cyclic+DREQ support, proven on
   this board by the display path. Using it is less new surface than
   writing a parallel one. The WO's "not a general dma.h
   implementation" rule was an anti-scope-creep constraint, not a
   requirement to avoid the existing driver.
2. **Resampler ratio.** The WO's §2 note says "OPL3 native ~49.7k";
   in SDLPoP the OPL3 emulator already resamples internally to the
   SDL rate, and the game opens at 44 100 Hz — so the backend's fixed
   ratio is 147:160 (44.1 k→48 k), applied to the final mix.
3. **MAI thresholds.** Linux gen1 values (PANIC 8/8, DREQ 6/8).
   Circle uses 16/16/16/16 on the same silicon — the documented
   fallback (`MAI_THR_VAL` in `hdmi_audio_init.c`) if DREQ pacing
   misbehaves at bring-up.
4. **Vorbis path has no assets.** This SDLPoP checkout's
   `data/music/` contains only `names.txt` (the ogg soundtrack is a
   separate upstream download), and the asset pack excludes `music/`.
   stb_vorbis is compiled and the mix path is exercised in sim, but
   on hardware "music" = OPL3/MIDISND. If oggs are added later, drop
   `music` from `EXCLUDE_DIRS` in `tools/pack_assets.py` (~35 MB
   image-size hit) or serve them from SD.

## Known issues / next steps

- **R3 pixel-clock coupling (standing constraint):** CTS is computed
  from the pixel clock at init and written once
  (`hdmi_audio_init.c`, comment at the CRP/CTS write). Any future
  HVS/video work that reprograms the pixel clock silently breaks
  audio clock regeneration — it must re-run `hdmi_audio_hw_init()`.
  This constraint must survive into future HVS work orders.
- **48 kHz / 2ch / S16 only** — by design (WO scope). The backend
  rejects any other SDL_OpenAudio spec.
- **Feeder scheduling:** the feeder runs cooperative (K_PRIO_COOP(7))
  and calls the game's mixer for ≤4 ms blocks. If HW shows underruns
  during heavy render scenes, the 8-block (32 ms) ring is the first
  knob (`AUDIO_NB`), thread priority the second.
- **Sim (qemu) has no HDMI**: the sim build stays on
  `SDLPOP_AUDIO_NONE`; the audio path's sim coverage is the host
  harness by design (freestanding C, no Zephyr headers).
- **hdmi_drive=2** now written by `install-to-sdcard.sh` and in the
  `config.txt` template; cards flashed before this change lack it.
- **CDC ACM shell didn't respond in the first HW session** (device
  enumerated, `tio` got no prompt). Matches the port's known
  boot-order behavior: the mini-UART USB adapter was connected to the
  host before boot, and/or the CDC cable was attached pre-boot —
  the documented workaround is to boot with the CDC cable (and
  ideally the UART adapter) unplugged and hot-plug after boot.
  Runtime hot-plug is proven fine on this board. Not audio-related
  (USB init at 0.212 s predates audio init at 0.765 s).
